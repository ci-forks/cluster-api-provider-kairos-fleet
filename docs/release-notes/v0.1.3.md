# v0.1.3

A maintenance release. **No functional change to the controller, the CRDs, the
cluster template or the RBAC** — `go.mod`, `api/`, `internal/`, `templates/`
and `config/` are untouched since v0.1.2. What changed is the toolchain the
binary is built with, and the repository's scanning and dependency tooling.

There are no migration steps from v0.1.2, and nothing in this release requires
you to upgrade. Take it if you want the rebuilt image.

## Changed

- **The controller image is built with Go 1.27** instead of Go 1.26, so the
  binary picks up the standard library fixes in that toolchain. The builder is
  still pinned by digest.

  `go.mod`'s `go` directive deliberately stays at 1.26.0. The builder only has
  to be *at least* the directive, not equal to it, and the directive cannot be
  raised past what golangci-lint is built with — the linter refuses to load a
  module targeting a newer Go than itself, and panics if the lint job merely
  installs one. The lint job is therefore pinned to Go 1.26 until a
  golangci-lint release is built on 1.27. The reasoning is recorded on both
  pins.

- **Scanning and dependency updates now follow the kairos-io org practice.**
  Trivy is replaced by Google's reusable OSV-Scanner workflow, which runs on
  pull requests, on pushes to `main`, and weekly, and reports into Security >
  Code scanning. Dependabot is replaced by Renovate (`renovate.json`), and
  Dependabot security updates are disabled at the repository level.

  One scope change worth stating plainly: Trivy scanned the built image
  including its base layer, while OSV-Scanner reads declared dependencies. Base
  image CVEs are now addressed by the digest bumps Renovate proposes rather
  than by a scanner.

- Renovate holds two groups for explicit approval on the dependency dashboard
  rather than opening them automatically, because each is one coordinated
  decision: the Go toolchain, and the Cluster API plus Kubernetes library set.
  The second is not theoretical here — Dependabot twice proposed moving
  `k8s.io/*` to v0.37.0 and controller-runtime to v0.25.0 while this provider
  pins `sigs.k8s.io/cluster-api v1.13.4`, which is built against the Kubernetes
  1.35 client libraries. Both proposals were closed; the grouping rule stops
  Renovate from inheriting the same behaviour.

- Release bodies now come from `docs/release-notes/<tag>.md`. Previously the
  workflow published GitHub's auto-generated commit list and the curated notes
  went nowhere, so v0.1.2's body had to be corrected by hand after the fact.
  This release is the first to use it.

## Upgrade notes

From v0.1.2 there are no migration steps, no CRD changes, and no behaviour
changes. A `clusterctl upgrade`, or re-applying the release manifest, picks up
the rebuilt image.

The prerequisites are unchanged, and both still matter on a fresh cluster: the
AuroraBoot nodes you claim must permit `apply-cloud-config`, `reboot` and
`reset` in `phonehome.allowed_commands`, and a cluster generated from the
template expects a worker join-token Secret. Both are covered in the
[quickstart](../QUICKSTART.md).

## Versions

Unchanged from v0.1.2: Cluster API v1.13.4 (v1beta2 contract), management
Kubernetes v1.32 to v1.36, Kairos v4.1.2. Workload Kubernetes is bounded by the
k3s or k0s version the Kairos image ships. Validated alongside
`cluster-api-provider-kairos` v0.1.3.
